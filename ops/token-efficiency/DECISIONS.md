# BSV binding decisions — compact ledger

- Existing Trader category is expanded; do not create a duplicate.
- AI category and Trader category both need major content growth.
- Trader end-state: BSV should let a motivated user build a personal chart tool with minimal coding.
- Add innovative reusable blocks/recipes/generators, not only a directory of platforms.
- Dots and Hugging Face are active AI expansion targets.
- Vela is a high-value custom-chart path.
- Third-party proprietary code must not be copied.
- Explicit compatible licenses are required for third-party source redistribution; otherwise create original source from public APIs/math.
- Verification must remain exact and scoped.
- Do not over-rely on local AI.
- LM Studio is available locally and should be used for cheap low-risk work where useful.
- Reduce ChatGPT/GrokBot token use with deterministic tooling, compact shared context, caching/routing where clients permit, and no duplicate reasoning.
- Owner should not need to intervene in routine execution.
- Toolkit summaries are public. BSV toolkit source (trader + AI) is served only behind the email-verified session gate (`/trading/items|downloads/bsv-*`, `/library/source/*`). Catalog status is shown verbatim, and Runtime-tested stays 0 without evidence.
- Live toolkit pages are generated by `scripts/site/build_live_toolkit.py` from the catalogs. Nobody edits that HTML by hand.
- Netlify CLI deploy layout keeps `netlify/`, `netlify.toml` and `node_modules` outside the publish dir. Deploy with `--prod` (production context). Never publish a CLI draft via `restoreSiteDeploy`: drafts run in `deploy-preview` context without production-only env (SMTP/operator email) — this broke OTP registration 16:04–16:23 JST on 2026-10-03.
- Site CSS/JS are `immutable`. Changed assets need new file names (content hash).
- New toolkit surfaces use the green accent, not gold.
- The 70 Library team implementations follow the source rule: explanation/files/examples public; full prompt/config/code only at `/library/source/team-*.html` behind the verified session; still labelled free. `items.json` carries no bodies.
- `*.bak*` backups and generator scripts are build artifacts, not site content; `gate_library_bodies.py` prunes them from every deploy tree (some held gated pages).
- The recipe builder is gated as BSV source: page `/trading/items/bsv-builder.html`, generator port under `/trading/sources/`. Its output must stay byte-identical to `render.mjs` (parity test).
- Logged-in QA uses the operator test account (`support@botshelfvampire.com`, name `OTP test`); its cookie jar stays on the box.
- Library pack items (skills, kimi-*, gemini, deepseek, cursor, claude-code, dify, flowise, autogen, openrouter, agentswarm, mcp, …) use the same body gate as the 70 teams: public explanation; full text at `/library/source/item-<runtime>-<slug>.html`; free label kept. `gate_library_bodies.py --packs all`.
- Trader generator/builder targets include MQL4, cTrader Python and Bookmap Python alongside Pine v6 / MQL5 / cTrader C#. Catalog status stays UNTESTED_RUNTIME until runtime evidence exists.
- Public GitHub repos (`botshelf-ai-team-registry`, `botshelf/packs`) stay public (owner decision). Site pages show them as provenance only (neutral "path in the BSV team registry repository" note); upstream/attribution links stay where a license requires them; they are never presented as BSV's gated body.
- `/cross-ai/kits/research-desk-local/` is left as is (owner decision); `test_library_gate.py` reports it as KNOWN_OUT_OF_SCOPE.
- Every deploy: confirm `/api/commerce/health` shows `email_configured:true`, deploy with `--prod`, confirm again (`qa/deploy_prod.sh`). Gated changes are verified LIVE (anonymous 302, test session 200 + byte match).
- Recipe builder share links/JSON carry only the user's own block config (whitelisted schema keys, plain param values). Never generated code or BSV source. The payload sits after `#` (not sent to a server); unchanged starters are shared by name; starter descriptions are dropped. Import/apply/download use the same sanitizer.
- Site pages are served with CSP `style-src 'self'`: no inline `<style>`/`style=` in generated pages; ship CSS as hashed files. QA browser checks must forward the CSP header.
- NinjaTrader 8 and Quantower are generator/builder targets (computing pattern like MQL5/cTrader). Catalog status stays UNTESTED_RUNTIME until real compile/runtime evidence exists.
- Builder recipe check (lint) and compile checklist are advisory: they never block rendering, sharing or download. Auto-fixes are limited to a stable dependency reorder and removing an unused block on click.
- AI per-task runners (LangGraph, CrewAI) never bundle Library team prompts. The user pastes the SYSTEM block from the gated `/library/source/team-<runtime>-<team>.html` page into `prompts/<task>.txt` (git-ignored). They write output only after an explicit "yes".
- "Official references" on toolkit pages list external docs only (no localhost or botshelfvampire.com URLs).
- Concurrent agents share the ops box and branch: before committing, deploying or posting the Issue #4 comment, fetch origin and check the latest Issue #4 comment and LIVE deploy, so the loop stays at one comment and no deploy is overwritten.
- No inline `<style>` or `style=""` in shipped HTML: `scripts/site/externalize_inline_styles.py` runs last in the pipeline and `--check` must report 0 before deploy. Gold accents inside moved CSS become the green accent (#bad4b7).
- Builder compile records are self-reported, kept in the browser (localStorage) and always `bsv_verified:false`; sending one to BSV is optional (see compile-result intake). They never change catalog status; "Runtime-tested by BSV" changes only with BSV's own evidence.
- Sierra Chart ACSIL and ProRealTime are generator/builder targets with UNTESTED_RUNTIME status. ProRealTime overlay recipes draw arrow markers; alerts need a second 0/1 indicator (stated in a TODO).
- n8n and OpenAI Agents SDK team runners follow the runner rule: prompts not bundled, local model, no write/send/paid steps without explicit approval (n8n workflows write/send nothing; Agents SDK runner saves only after "yes", tracing disabled).
- "Official references" exclude non-public hosts (localhost, 127.0.0.1, 0.0.0.0, host.docker.internal, URLs with ports).
- No gold accents in site CSS (owner rule, cycle 7): `recolor_accent.py` runs after `externalize_inline_styles.py` in the pipeline; `--check` must report `[]` before deploy. Recolored CSS gets a content-hashed name (`.g<sha8>.css`) because CSS is cached immutable for 1 year.
- MotiveWave and Vela are generator/builder targets with UNTESTED_RUNTIME catalog status. A javac compile against BSV-written javadoc stubs and a headless smoke test with synthetic bars are recorded as what they are; they do not change "Runtime-tested by BSV".
- The Vela target must stay free of the Pine addon (`@luxalgo/vela-pinets`/`pinets`, AGPL-3.0): it imports only `@luxalgo/vela` (Apache-2.0) and ships its own plain-JS engine.
- Compile-result intake (if built) is owner-reviewed: no auto-promotion and no "verified" state; approved user reports show as "user-reported", never "verified by BSV".
- Compile-result intake is built with the owner's most conservative answers (2026-10-03, cycle 8): email-verified accounts only; stored server-side in the existing Netlify Blobs setup (store `compile_reports`, keyed to the account id); no PII beyond the existing account email (looked up at review time, not copied); owner-only review queue (`x-admin-secret`); never auto-promoted, no `verified` state, `bsv_verified:false` always; approved reports stay internal (no public display); failed-compile reports are not public; rejected reports are deleted 30 days after review; 10 per account per day; no email sent on submit or review. Function source lives in `site-functions/` and is copied into the deploy root by `install_compile_report_fn.py`.
- JForex (Dukascopy) is a generator/builder target with UNTESTED_RUNTIME status: one `IStrategy` class that reads closed bars via `IIndicators`/`IHistory` and prints values/alerts to the JForex console. It never uses `IEngine` and places no orders (`check_jforex_stubs.sh` fails if it does). The javac compile against BSV-written javadoc stubs is recorded as exactly that, not a JForex compile.
- TradeStation EasyLanguage is a generator/builder target with UNTESTED_RUNTIME status: an indicator only (plots + `Alert` on `BarStatus(1) = 2`), no strategy order words. Crosses are explicit comparisons so all targets share one cross rule. BSV has no TradeStation verifier; `check_easylanguage_output.mjs` is a structural check and is reported as such.
